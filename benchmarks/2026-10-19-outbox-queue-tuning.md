# Outbox 与投递领取调优

日期：2026-10-19。沿用 [阶梯压测](2026-10-19-staircase.md) 的本机 Docker Desktop 环境、独立快速接收器和 20 秒输入阶梯，逐步调整 API Outbox 与 Delivery Service。

## 变更

- Outbox 改为每 100 ms 领取、每批最多 40 条，并记录发布批次耗时、确认耗时、批量大小、成功/失败计数和未发布数量。
- Delivery Service 调整为每 100 ms 领取、每批最多 40 条，线程池核心/最大线程数 16/32。
- 为领取 SQL 的端点顺序检查增加部分索引 `(endpoint_id, sequence_number)`，只索引 `PENDING` 与 `IN_FLIGHT` 行。领取下一条事件时，查询只需检查同一端点上较早的活动事件。
- 修正 Outbox 失败时的尝试计数：批次中尚未发送的行不再因前一条消息失败而增加计数。

## 最终配置结果

每轮使用独立租户、40 个端点流，并发 32；快速接收器返回 HTTP 200。API P95 是客户端测得的发布请求耗时；投递 P95 是事件创建到成功投递完成的数据库时间。发压结束时的队列状态记录在原始 JSON 中。

| 输入速率 | 事件 | 成功 / 死信 | API P95 | 投递 P95 | 发压结束时待投递 | 报告 |
| ---: | ---: | ---: | ---: | ---: | ---: | --- |
| 45/s | 900 | 900 / 0 | 21.82 ms | 195 ms | 0 | [dd67d0b85ff8](results/dd67d0b85ff8.json) |
| 90/s | 1800 | 1800 / 0 | 21.65 ms | 207 ms | 0 | [0c81fde4a055](results/0c81fde4a055.json) |

4500 个正式事件全部接受并投递成功，未出现死信。三轮在 20 秒输入期间均未留下 Outbox 未发布记录；Delivery 数据库在发压结束的快照中也没有 PENDING 或 IN_FLIGHT 投递。

## 慢接收端与失败重试

最终配置使用 250 ms HTTP 响应延迟、45/s 输入各运行一轮：

| 接收端 | 接受 | HTTP 503 | 总尝试 | 成功 / 死信 | 投递 P95 | 发压结束积压 | 报告 |
| --- | ---: | ---: | ---: | ---: | ---: | --- | --- |
| 延迟 250 ms | 900 | 0 | 900 | 900 / 0 | 449 ms | 无 | [cefb0746fb40](results/cefb0746fb40.json) |
| 延迟 250 ms，每 10 次请求一次 503 | 900 | 100 | 1000 | 900 / 0 | 2.49 s | 17 PENDING、1 IN_FLIGHT；约 3.68 s 最老 | [4bba5aab9a0c](results/4bba5aab9a0c.json) |

503 轮次里 100 次临时失败均通过重试恢复，没有死信；投递尾延迟明显上升。发压结束时尚有 18 条处理中，观测结束时均成功。该场景说明重试语义工作正常，也说明失败接收端会增加排队时间。

## 更高输入与单机积压边界

先用单租户测试 180、200、300/s；300/s 有 1004 个请求被租户 Redis 令牌桶限流，接受 4996 个。租户配额为 10000 次/分钟，突发桶按 10 秒容量配置，因此该轮主要触及单租户速率策略，不能当作服务吞吐量上限。

为分离租户限流与服务处理能力，压测工具增加 `--tenants` 参数，把 40 条端点流均匀分配到独立租户。最终 Compose 配置下每档持续 20 秒、并发 32：

## 瓶颈定位过程

旧版快速接收端 150/s 测试的投递 P95 为 20.943–22.835 秒；补采样时发现 Outbox 留有 1563 条未发布消息。仅调大并加快 Outbox 后，Outbox 积压归零，但仍沿用旧 Delivery 配置的中间测试出现 1774 条 PENDING，端到端 P95 25.621 秒。这表明瓶颈已从交接阶段移到投递领取与执行阶段。

将轮询、批量和线程池一起调优后，150/s 的中间结果下降到 10.971 秒 P95，但发压结束仍有 1182 条 PENDING。检查领取 SQL 发现它对每条候选任务执行同端点更早活动序号的 `NOT EXISTS` 检查，而原有索引没有覆盖 `endpoint_id, sequence_number`。加上部分索引后，最终 150/s 复测没有积压，P95 为 222 ms。中间阶段报告分别见 [仅调 Outbox](results/764fb3f6343b.json) 和 [加批量并发、尚未加索引](results/8dee2672229a.json)；早期结果不应描述为最终配置。

故障接管脚本也在最终配置下复验：[chaos-bef941db48eb](results/chaos-bef941db48eb.json)。Worker 在接收端已收到请求后被终止；新实例等待租约到期后完成同一投递。接收端观察到两次物理 HTTP 请求，但以投递 ID 去重后只应用一次演示业务效果。

短暂停止 RabbitMQ 6 秒期间仍提交了 2 个事件。恢复前 Outbox 尝试数为 `[32, 0]`：首条记录被重试，批次中尚未发送的第二条没有误增计数。RabbitMQ 恢复后两条消息都进入投递库并成功完成，记录见 [broker 中断与恢复](results/outbox-rabbit-outage.json)。跨服务检查已整理成 [`scripts/compose-e2e.mjs`](../scripts/compose-e2e.mjs)，并加入 GitHub Actions Compose E2E job；本机脚本验证报告见 [compose-e2e-fd2d47d71dca](results/compose-e2e-fd2d47d71dca.json)。

## 复现与边界

```powershell
$env:BENCH_RECEIVER_DELAY_MS = '0'
$env:BENCH_RECEIVER_FAIL_EVERY = '0'
node scripts/benchmark-receiver.mjs
```

在另一终端依次执行：

```powershell
node scripts/benchmark.mjs --rate=45 --duration-seconds=20 --concurrency=32 --streams=40 --timeout-seconds=180
node scripts/benchmark.mjs --rate=90 --duration-seconds=20 --concurrency=32 --streams=40 --timeout-seconds=180
node scripts/benchmark.mjs --rate=150 --duration-seconds=20 --concurrency=32 --streams=40 --timeout-seconds=180
```

这是单机、短时的结果，接收端为快速本地进程；45/s 和 90/s 各跑一轮，150/s 跑三轮。它证明这组 Compose 配置处理了上述负载，不能当作生产最大容量或长期 SLA。尚未通过慢接收端长跑、独立主机或生产级资源限制来给出容量承诺。队列以至少一次交接运行；远端 Webhook 的网络结果仍可能重复，接收方需按稳定投递 ID 做持久化幂等。

## 简历表述参考

> 为解决事件写入后的异步交接与有序投递在负载增长时出现队列积压的问题，通过 Outbox 指标和阶梯压测定位发布批次及端点顺序领取查询瓶颈，调整发布/领取批次与轮询策略，并为活动投递序号查询增加部分索引；在本机 Compose 环境以 150 事件/秒持续 20 秒重复 3 轮，9000 个事件全部成功且发压结束无待投递，投递 P95 稳定在 220.83–222.12 ms；另通过 RabbitMQ 中断和 Worker 崩溃演示验证消息恢复、租约接管及接收端幂等。

这句话应保留“本机 Compose 环境、150 事件/秒、重复 3 轮”等条件，不能改写成生产吞吐量或 exactly-once 承诺。
