# 容量评估与生产部署边界

RelayBox 当前 Compose 与压测数据用于本地开发和方案验证，不是可直接上线的生产部署包。以下流程用于把“本机跑过多少事件”变成有明确边界的容量结论。

## 先定义服务目标

压测前填写这些输入，缺一项就不要把结果称为容量：

| 输入 | 需要明确的值 |
| --- | --- |
| 峰值入口速率 | events/s，以及峰值持续多久 |
| 日常负载 | events/s 与每日事件量 |
| 事件与投递扇出 | payload 大小分布、每个事件平均匹配的端点数 |
| 顺序约束 | 热门端点流量占比；同一端点严格顺序会限制并行度 |
| 接收端行为 | 成功、慢响应、429、5xx、超时的比例与延迟分布 |
| 服务目标 | API 接受率、API P95/P99、投递完成 P95/P99、恢复时间 |
| 数据保留 | 事件、投递和尝试记录分别保留多久 |

容量应按“事件入口”和“Webhook HTTP 投递”分别报告。一个事件可能匹配多个端点，因此入口 events/s 不等于投递 requests/s。

## 测量步骤

1. 在与目标部署相同的 CPU、内存、PostgreSQL 版本、磁盘类型和网络环境中运行。记录镜像版本、配置、数据库规格、Worker 数量和连接池大小。
2. 让负载逐级上升。每个档位至少重复三轮，并包括持续负载、突发负载和长时间 soak run。每轮使用独立租户和事件类型，保存原始 JSON 与容器资源指标。压测脚本单轮最多 10,000 个事件，固定速率持续时间最长 600 秒；例如 `--rate=15 --duration-seconds=600` 可用约 9,000 个正式事件做 10 分钟 soak。
3. 每轮加入可控的慢响应、429、5xx 和超时比例，验证退避、熔断和数据库增长情况。快速返回 200 的接收端只能测出无故障条件下的结果。
4. 判定稳态时，确认队列最老任务年龄和积压没有持续上升，同时 API 与投递延迟满足目标。某一轮最终清空了队列，不代表该负载可长期承载。
5. 在目标负载下停止一个 Worker、重启 API、重启数据库或注入接收端故障，记录积压恢复时间。容量结果应包含故障条件和恢复目标。
6. 用更高的峰值和长期 soak 再验证资源余量；将通过的配置作为已验证档位，而不是声称测得绝对最大值。

当前脚本 `scripts/benchmark.mjs` 会记录主机与 Docker CPU/内存、Worker 数量、固定速率、API 延迟样本、投递 P50/P95/P99、发压结束时的待投递数量和积压年龄、失败数和压测报告。`relaybox.delivery.queue.oldest.pending.age` 指标提供一个全队列积压年龄信号；与队列深度、投递延迟、数据库 CPU/IO、连接池等待和重试率一起观察。该指标按 `created_at` 计算最老待处理投递年龄，会包含因端点顺序而等待的后续任务。

当前已有本机数据：在 1 个 API、1 个 Delivery Service、40 条有序端点流、快速 HTTP 200 接收端、Docker Desktop（32 vCPU）条件下，200 events/s 持续 30 秒完成 6,000 个事件（API P95 16 ms、投递 P95 240 ms、0 积压）；2,000 个事件以约 618 events/s 突发提交全部接受，但投递 P95 约 5.96 秒。历史调优记录中 250 events/s、2 个租户仍全部成功，275 events/s 起开始出现 Outbox 积压，400 events/s 投递 P95 约 14.95 秒。这不是生产容量，也没有覆盖慢接收端、持续失败、HA 故障切换或长时间数据增长。详情见 [2026-10-22 收尾复测](../benchmarks/2026-10-22-revalidation.md) 和 [Outbox 与投递队列调优](../benchmarks/2026-10-19-outbox-queue-tuning.md)。

## 按观测结果扩展

- **Worker CPU 或 HTTP 执行槽先饱和**：逐步增加 Worker 副本或每实例并发，并同时观察数据库连接、锁等待和投递延迟。按每个 Worker 的实际连接池限制控制总连接数。
- **数据库先饱和**：停止加 Worker。先用 `EXPLAIN (ANALYZE, BUFFERS)` 检查领取和状态更新查询，观察 WAL、磁盘延迟、锁冲突和 autovacuum；对大表设定保留及归档策略，再评估按状态/时间分区、读写拆分或分区队列。
- **少数端点造成排队**：端点内顺序意味着单个热端点基本串行；扩 Worker 不会提升该端点的并行度。需要与租户协商放宽顺序、按业务键分组，或将顺序分区并行化。
- **轮询空耗明显**：比较轮询频率、空轮询 DB 负载和队列延迟，再决定是否引入通知机制；不能只优化延迟而忽略数据库成本。
- **单库故障或恢复目标不满足**：部署 PostgreSQL 高可用与备份恢复演练，确认连接重试、故障切换时的租约行为和 RPO/RTO。增加数据库副本不能自动解决写队列的主库瓶颈。

达到单 PostgreSQL 的可测上限后，再考虑用 outbox/CDC 把提交事件转发到 Kafka 等分区队列。迁移前应先明确分区键、端点顺序语义、重放、保留期限和双写切换方式；消息中间件本身不会消除接收端幂等要求。

## 生产环境上线前必须改变的配置

当前 `compose.yaml` 是单机开发环境：数据库凭证是示例值，测试接收器启用，允许私网 Webhook 目标，PostgreSQL 数据库端口映射到本机，且没有提供 TLS 入口、密钥管理、数据库 HA、备份恢复或自动扩缩容配置。生产部署至少需要：

- 使用密钥管理系统提供主密钥和数据库凭证；禁止使用仓库中的本地默认值。
- 关闭 `TEST_RECEIVER_ENABLED`，保持私网目标限制，并用网络出口策略阻止访问云元数据和内部管理网段。
- 通过 TLS 入口发布 API，数据库只放在私有网络，不直接向公网暴露。
- 为 PostgreSQL 配置高可用、加密备份、恢复演练、容量告警和数据保留/归档策略。
- 配置请求体上限、连接/线程池边界、速率限制、告警、审计日志、trace 与发布回滚机制。
- 完成目标云和目标规格上的负载、故障注入与恢复时间验证后，再对外公布 SLO 或容量承诺。
