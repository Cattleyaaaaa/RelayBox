# RelayBox 面试演示：三分钟讲清可靠投递

## 开场（约 20 秒）

RelayBox 是一个多租户 Webhook 投递平台。事件 API 与 Delivery Service 独立部署、使用不同 PostgreSQL 数据库；API 通过事务性 Outbox 和 RabbitMQ 将事件交给 Delivery Service，后者用幂等 Inbox 落盘并执行有序投递。

## 现场演示（约 2 分钟）

1. 打开 `http://localhost:3005` 的“演示中心”，连接本地租户，并填写本地演示主密钥。
2. 运行自动重试演示：接收端两次 HTTP 500 后返回 200。指出逐次尝试记录来自 PostgreSQL。
3. 在任意 PowerShell 目录运行 `& 'D:\DeskTop\后端学习\backend\scripts\chaos-recovery.ps1'`，同时观察“故障接管现场”。脚本自动暂时停止正常 Delivery Service、创建独立故障服务副本，并在结束后恢复原数量。
4. 指向四个阶段：首请求到达、租约过期、另一个 Delivery Service 实例重领、接收端去重。最后让面试官看到“两次 HTTP 请求、两条持久化尝试、一次演示业务效果”。

若项目路径不同，改用实际的 `scripts/chaos-recovery.ps1` 绝对路径。不要在生产环境或共享数据库运行故障脚本。

## 面试官可能追问

**为什么不能保证端到端 exactly-once？** 请求已被接收方处理，但 Worker 在收到响应前死亡时，发送方无法确定处理是否发生。租约恢复后必须再次发送；接收方要以投递 ID 做持久化幂等，并将去重与业务写入放在同一事务里。演示接收端用 PostgreSQL 唯一键持久化去重，并用一条记录模拟业务效果；真实接收方仍要在自己的事务中原子地完成去重和业务修改。

**多个 Worker 为什么不会同时领取同一任务？** PostgreSQL 行锁与 `FOR UPDATE SKIP LOCKED` 用于领取，领取状态和尝试记录在事务中提交。崩溃后超过租约的尝试被关闭，任务重新入队。端点内用序号阻塞后续未完成投递，端点之间可并行。

**Outbox 与 Inbox 各解决什么问题？** Outbox 避免业务事件已写入数据库、但消息未发到 RabbitMQ 的双写丢失；publisher confirm 后标记发送，崩溃窗口仍可能重复发布。Inbox 用事件 ID 唯一约束吸收重复消息，并在同一事务创建投递任务。

**性能证据是什么？** 当前 Compose 在本机做了六轮 45 事件/秒、每轮 30 秒的固定负载对照，1 个和 2 个 Delivery Service 副本均接受并成功投递 4050 个事件，0 拒绝、0 死信；投递 P95 分别在 452.84–457.74 ms 和 452.40–457.27 ms。该负载下没有测出扩容收益，也没有测到容量上限。环境、逐轮原始数据和局限见 `benchmarks/2026-10-19-microservices.md`。

**接收端收到同一投递 ID、不同内容怎么办？** 不应静默当作重复成功。演示接收端比较事件 ID 与 JSONB 内容；不一致时返回 HTTP 409，并在现场显示为幂等键冲突。真实接收端也应记录和告警这种冲突，检查签名密钥、发送方数据或接收端实现。

当前增加的 `relaybox.delivery.queue.oldest.pending.age` 指标用于观察排队老化；它与队列深度、延迟、数据库资源和失败率一起判断是否稳态。容量评估方法与当前生产部署缺口见 `docs/production-capacity.md`。

## 简历可用表述

> 针对事件写入与异步投递跨服务时的双写丢失和重复消费风险，将多租户 Webhook 平台拆分为独立 Event API 与 Delivery Service，分别使用 PostgreSQL；通过事务性 Outbox、RabbitMQ publisher confirm 和幂等 Inbox 实现可恢复的至少一次事件交接，并在投递端实现 `SKIP LOCKED`、租约恢复和端点有序重试。通过容器故障注入验证服务实例中断后的租约接管：两次 HTTP 请求共用同一投递 ID，接收端持久化业务效果仅一次；本机六轮固定负载共完成 8100 个事件投递，45 事件/秒下投递 P95 约 453–458 ms。

不要写“生产级”“严格 exactly-once”“保证所有情况下零重复”或未经测量的峰值吞吐。
